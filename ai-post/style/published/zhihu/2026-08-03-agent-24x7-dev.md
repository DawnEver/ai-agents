先说我的核心判断：Agent 时代，软件开发不再是「写代码的规则」，而是「运行优化器的规则」。

这套判断不是我空想出来的，是用 Claude Max 20x 7×24 迭代一个大型项目一个月后，沉淀下来的一整套原则。最扎心的一次：Agent 跑通宵，pytest 全绿，第二天我试那功能，完全不是我要的东西——问题不在代码，在目标函数，我从没告诉它「什么才算对」。

## 前提：软件开发是优化问题，不是写作问题

软件工程 = 把自然语言意图（Intent）转化为确定性机器代码。输入模糊意图，输出运转良好的系统。Agent 不再「一步写对」，而是反复迭代实现，本质是一个多目标优化器在解空间搜索，三个目标互相拉扯：

| 目标 | 含义 | 失败的症状 |
|------|------|-----------|
| f1 语义正确性 | 代码是否符合用户模糊的业务意图 | 代码能跑，但不是用户要的 |
| f2 系统稳定性 | 边界条件、异常下是否鲁棒 | 正常路径绿，边界路径静默错 |
| f3 计算成本与效率 | 步数、API 次数、token/时间是否可接受 | 上下文打满、烧穿 token、超时 |

这三个目标必须**显式化为可度量的目标函数**，而不是「尽力把事做好」。整套原则只回答一个问题：如何让这个优化器持续、诚实、低成本地逼近最优解。

## 一、第一约束是诚实：目标函数撒谎，整个搜索方向就错了

优化器沿着目标函数走。函数一旦撒谎，走得越远越错——这是 Agent 时代最常见的系统性失败。

- **准确是标签，不是门槛。** f1 必须量化：任何能运行的组合都走同一条路径，返回结果 + 机器可读精度标签 + 实测偏差的 warning。绝不编造数字。
- **声明不得撒谎**（最常见的缺陷类别）。优化器读的目标函数——docstring、注释、类型提示、状态——必须是代码强制查阅的，不是读者只能信任的。最危险的是守卫范围撒谎：它让你绕过仍然工作的检查，所以范围声明要有专属测试。
- **验证「是否真的修复」：revert it, keep the prose, run the suite。** 回退修复、保留文档、重跑套件，看它是否又红——这是区分「已修复」和「声称已修复」的唯一工具。
- **实现，而非排除。** 别用「能力守卫」把不精确的组合挡在门外；隐藏约束会遮蔽真实解空间。

## 二、系统稳定性是一等目标：边界条件是显式失败，不是隐形错误

f2 的判据不是「不崩」，而是每个失败模式都被显式声明并可达。

- **不支持的组合直接抛异常（RAISE），绝不静默失败。** 能力/方法覆盖是声明数据，不是优化器探测不到的坑。
- **适配器返回完整、干净的输出。** 半模型、对称折叠活在适配器内部，绝不泄露到组合层——否则组合层根本不知道哪个组件在撒谎。
- **禁止 waivers、fallback、_legacy 包装。** 稳定性不允许用「绕过」换取表面通过；可触达的修复，才是修复。
- **删除是事件，退役是属性——登记而非记住。** 要下线一个能力，别偷偷兼容旧逻辑：退役拼写进入 retired.py（注明替代与原因），与重构同次提交，并有测试覆盖它确实下线了。

## 三、计算成本与时间预算是硬约束

f3 是约束，不是目标——成本超限，意味着这个「层」已经不存在了。

- **反馈循环分级时间预算**（经验值）：冒烟 5–10 分钟 → 阻塞门 ≤30 分钟 → 其余永不阻塞。
- **预算是等待的上限，不是工作的上限。** 超限就拆分、并行、或移出阻塞路径。
- **Token 预算是硬约束，要实测。** 我实测 20× Claude Max 对一个大型求解器项目都堪堪不够——额度必须按项目规模真实计量，而不是拍脑袋。预算 = 每轮可消耗的 token + 何时 compact + 何时切便宜模型。
- **分层调用模型。** 昂贵模型做决策与关键节点，便宜模型（用 fabric 调 deepseek / codex）做重活与机械执行。用 token 换 token：把耗 token 的体力活下放到便宜模型。

## 四、7×24 迭代的组织：从「一次会话」到「持续运行的优化器」

让 Agent 7×24 迭代，关键是把记忆与计划从「会话上下文」中解放出来。

- **计划依赖树（Plan Dependency Tree）。** 主 Agent 维护动态计划，每个节点只留 Task_ID、Status、不超过 500 token 的上下文摘要（Context_Digest，经验值）、后续任务编号（Follow_up_Ids）。计划由 rem 记忆系统制定并持续更新，跨会话持久化——会话断了，下一个也能从记忆接住。goal 要求完成全部计划及其 follow-up，不留隐性收尾。
- **主 Agent 绝不亲自重度编码。** fan-out subagent 执行具体任务，主会话上下文得以保全——这是防止主会话打满的根本手段，不是优化项。它只答三件事：谁依赖谁、谁完成了、下一步派谁。
- **多目标收敛由套件裁决，不由人记忆。** 目标函数值由统一 gate 自动裁决（PASS / FAIL / INCONCLUSIVE 三态），不用手写测试脚本人工判断。缺失日志 = 「未完成」，从不等于「未开始」。
- **根因修复 + 登记退役。** 每次迭代从干净起点出发，把技术债转化为显式、可消化的队列。
- **单一验收标准。** 优化过程中 f1/f2/f3 三个子目标相互权衡，但每次验收收敛只认一个综合目标函数（命名统计量的常量，无 per-case 覆盖），绝不写评判它的 bar。多套标准互相打架 = 优化器在不连续的目标面上振荡。

## 一句话总纲

Agent 时代，软件开发 = 一个**持续运行的多目标优化器**（语义正确、系统稳定、成本受控）。原则只有三条：**目标函数必须诚实、边界必须显式、预算必须实测。**

主 Agent 从「写代码的人」退位为「调度优化器的控制器」——用记忆系统接住跨会话的计划，用 fan-out 保住主上下文，用分层模型控住 token，用套件作为唯一的收敛判据。所谓控制器，就是在 token 烧穿之前，知道该让谁去干。
