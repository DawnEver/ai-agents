有一次我让 Claude Code 跑通宵，第二天一早打开，pytest 全绿，跑得比谁都顺。可我一试那功能，完全不是我要的东西。问题不在代码，在目标函数——我根本没告诉它「什么才算对」，它就在错误的目标上完美地跑了一整夜。

这件事让我想明白：Agent 时代的软件开发，不再是「写代码的规则」，而是「运行优化器的规则」。下面这套，是我使用 Claude Max 20x 7×24 迭代一个大型项目一个月后，沉淀下来的一整套原则。

## 〇、前提转变：软件开发是优化问题，不是写作问题

软件工程，就是**把人类的自然语言意图（Intent），转化为确定性机器代码**。输入是模糊意图，输出是运转良好的系统。

Agent 不再「一步写对」，而是反复迭代实现。它本质上是一个**多目标优化器在解空间里搜索**，三个目标互相拉扯：

- **f1 语义正确性**——生成的代码，到底对不对得上用户脑子里那个模糊意图。失败的症状很扎心：**代码能跑，但不是用户要的**。
- **f2 系统稳定性**——边界条件、异常之下，Agent 组合出的系统是否鲁棒。失败的症状：**正常路径全绿，边界路径静默出错**。
- **f3 计算成本与效率**——思考步数、API 调用次数、token 和时间成本，是否扛得住。失败的症状：**上下文打满、烧穿 token、超时**。

这三个目标，必须**显式化为可度量的目标函数**，而不是「尽力把事做好」。整套原则，只回答一个问题：**如何让这个优化器持续、诚实、低成本地逼近最优解。**

## 一、第一约束是诚实：目标函数撒谎，整个搜索方向就错了

优化器沿着目标函数走。如果目标函数本身撒谎，走得越远越错——这是 Agent 时代最常见的系统性失败。

**准确是标签，不是门槛。** f1 必须被量化：任何能运行的组合都走同一条路径，返回结果、机器可读精度标签、以及实测偏差的 warning。绝不编造数字——那个「~X% 偏差」，是让发布诚实的唯一根据。

**声明不得撒谎。** 这是最常见的缺陷类别。优化器读的「目标函数」——docstring、注释、类型提示、状态——必须是代码强制查阅的，而不是读者只能信任的。最危险的是守卫范围撒谎：它让你绕过仍然工作的检查。所以范围声明要有专属测试：在目标区域种下哨兵测试。

**验证「是否真的修复」：revert it, keep the prose, run the suite。** 优化器判断收敛的唯一方法，是回退修复而保留文档，看套件是否又红。这是区分「已修复」和「声称已修复」的唯一工具。

**实现，而非排除。** 不要用「能力守卫」把不精确的组合挡在门外；在工作目标函数里塞隐藏约束，会遮蔽真实解空间。

## 二、系统稳定性是一等目标：边界条件是显式失败，不是隐形错误

f2 的判据不是「不崩」，而是**每个失败模式都被显式声明并可达**。

**不支持的组合直接抛异常（RAISE），绝不静默失败。** 能力/方法覆盖是声明数据，不是优化器探测不到的坑。

**适配器返回完整、干净的输出。** 半模型、对称折叠，都活在适配器内部，绝不泄露到组合层。稳定性的前提是组件边界清晰——否则组合层根本不知道哪个组件在撒谎。

**禁止 waivers、fallback、_legacy 包装。** 稳定性不允许用「绕过」换取表面通过；一个可触达的修复，才是修复。

**删除是事件，退役是属性——登记而非记住。** 要下线一个能力，别偷偷兼容旧逻辑：退役拼写进入 retired.py（注明替代与原因），与重构同次提交，并有测试覆盖它确实下线了。让优化器每次迭代都从干净起点出发，不背历史债。

## 三、计算成本与时间预算是硬约束

f3 是约束，不是目标——成本超限，意味着这个「层」已经不存在了。

**反馈循环分级时间预算**（经验值）：冒烟 5–10 分钟（diff 挑选）→ 阻塞门 ≤30 分钟（工具拒绝超限）→ 其余无上限且永不阻塞。

**预算是等待的上限，不是工作的上限。** 超限就拆分、并行、或移出阻塞路径。

**Token 预算是硬约束，要实测。** 我实测过：20× Claude Max 的额度，对一个大型求解器项目都堪堪不够。这证明额度必须按项目规模真实计量，而不是拍脑袋。预算 = 每轮迭代可消耗的 token + 何时 compact 的时机 + 何时切换便宜模型的时机。

**分层调用模型。** 昂贵模型做决策与关键节点（计划、验收、批判性审查），便宜模型（用 fabric 调 deepseek）做重活与机械执行。用 token 换 token：把耗 token 的体力活下放到便宜模型。

## 四、7×24 迭代的组织：从「一次会话」到「持续运行的优化器」

让 Agent 7×24 迭代，关键是把**记忆与计划从「会话上下文」中解放出来**。

**计划依赖树（Plan Dependency Tree）。** 主 Agent 维护动态计划，每个节点只留四样东西：Task_ID、Status（Pending/Running/Success/Failed）、一段不超过 500 token 的上下文摘要（Context_Digest，经验值）、以及它衍生出的后续任务编号（Follow_up_Ids）。计划由 rem 记忆系统制定并持续更新，跨会话持久化——这样就算会话断了，下一个会话也能从记忆里接住没做完的计划。设 goal 要求完成全部计划及其 follow-up，不留隐性收尾。

**主 Agent 绝不亲自重度编码。** fan-out subagent 执行具体任务，主会话上下文得以保全——这是防止 Main Session 上下文打满的根本手段，不是优化项。它只回答三件事：谁依赖谁、谁完成了、下一步派谁。

**多目标收敛由套件裁决，不由人记忆。** 每次迭代的「目标函数值」由统一 gate 自动裁决（PASS / FAIL / INCONCLUSIVE 三态），不需要手写测试脚本去人工判断。可选组经 gate 标志运行，绝不靠手设变量。缺失日志 = 「未完成」，从不等于「未开始」。

**根因修复 + 登记退役。** 让优化器每次迭代都从干净起点出发，把累积技术债转化为显式、可消化的队列。

**单一验收标准。** 优化过程中 f1/f2/f3 三个子目标相互权衡，但每次验收收敛只认一个综合目标函数（命名统计量的常量，无 per-case 覆盖），绝不写评判它的 bar。多套标准互相打架 = 优化器在一个不连续的目标面上振荡。

## 一句话总纲

Agent 时代，软件开发 = 一个**持续运行的多目标优化器**（语义正确、系统稳定、成本受控）。

原则只有三条：**目标函数必须诚实、边界必须显式、预算必须实测。**

主 Agent 从「写代码的人」退位为「调度优化器的控制器」。所谓控制器，就是在 token 烧穿之前，知道该让谁去干、该问谁。我把它写下来，是因为那晚的教训还在：代码会跑，不代表它是对的。
